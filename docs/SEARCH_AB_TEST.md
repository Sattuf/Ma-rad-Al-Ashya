# تجربة ترتيب نتائج البحث — Search Ranking A/B Test

## السؤال

هل يجعل **الترتيب الذكي (A)** الباحثين ينقرون على نتيجة أكثر من **الأحدث أولاً (B)**؟

- الترتيب الذكي يجمع: الصلة بالنص، والتفاعل (النقرات والرسائل)، وجودة الإعلان، والترويج.
- المقياس: **نسبة النقر** = عمليات بحث انتهت بنقرة ÷ عمليات البحث، لكل خوارزمية.

## المسار

```
الويب / الجوال ── GET /api/v1/search?q=…&session_id=… ──▶ البوابة (لا كاش لهذا المسار)
                                                        │
                                                        ▼
                                   search-service:
                                     1. يعيّن الخوارزمية (ثابتة لكل حساب، وإلا لكل زائر)
                                     2. يرتّب المعرّفات في Elasticsearch
                                        (يستبعد المباع والمنتهي والمحذوف، ويدعم الصفحات)
                                     3. يعدّ «عملية بحث» للصفحة الأولى فقط
                                                        │  { ids, total, page, limit, variant }
                                                        ▼
الويب / الجوال ── GET /api/v1/listings?ids=… ──▶ listings-service
                  (دفعة واحدة، بالترتيب نفسه، وتُسقط الإعلانات غير المنشورة)
        │
        └─ نقرة على نتيجة ── POST /api/v1/search/track-click { variant, position, … }
                             ├─ صف في ab_test_results (للإحصاءات)
                             └─ search:clicks:{id} في Redis (إشارة ترتيب لمدة 30 يوماً)
```

- **التصفح دون نص** (قسم أو سعر فقط) يقرأ من قاعدة البيانات مباشرة وليس جزءاً من التجربة.
- **إن تعطّلت خدمة البحث** تعمل نفس العبارة على قاعدة البيانات:
  - يرى المستخدم نتائج دائماً.
  - هذه الصفحات بلا خوارزمية، فلا تُعدّ ولا تُسجَّل نقراتها.

## ضمانات صحة القياس

| الخطر | الضمان |
|---|---|
| مستخدم يختار خوارزميته (`ab_variant`) | يُتجاهل؛ التعيين في الخادم فقط |
| الهوية من ترويسة يرسلها العميل | الهوية من رمز JWT مُتحقَّق منه فقط؛ الرمز غير الصالح = زائر |
| كاش البوابة يمنع وصول البحث إلى الخدمة فلا يُعدّ | `/search` خارج كاش البوابة (مغطى باختبار) |
| تصفّح الصفحات يضخّم عدد عمليات البحث | تُعدّ الصفحة الأولى فقط |
| إعادة التحميل أو تكرار العبارة نفسها تضخّم العدد | «بحث» واحد لكل (زائر، عبارة وفلاتر) كل 30 دقيقة |
| الكتابة في الجوال تُعدّ كل جزء من الكلمة بحثاً | الجوال يستخدم التجربة عند الإرسال أو اختيار اقتراح فقط، كما في الويب |
| تزوير النقرات لرفع إعلان في الترتيب أو إفساد النتائج (المسار بلا تسجيل دخول) | تُقبل النقرة فقط إن طابقت خوارزمية الزائر المعيّنة، وكان الإعلان ضمن ما عُرض عليه خلال 30 دقيقة، ومرة واحدة لكل زائر وإعلان. غيرها يُرد `{tracked:false}` ولا يُحتسب |
| طلبان متزامنان لزائر جديد يسحبان خوارزميتين مختلفتين | `SET NX` ثم قراءة القيمة المخزنة |
| زوار بلا تخزين محلي يتشاركون معرّفاً واحداً فيقعون في خوارزمية واحدة | معرّف عشوائي لكل تحميل صفحة عند تعذّر التخزين |
| صفحات تتجاوز نافذة Elasticsearch (10,000 نتيجة) فتفشل وتختلط بنتائج قاعدة البيانات | الصفحات والعدد الكلي محدودان بالنافذة |
| النقرة تُحتسب مشاهدة مرتين | النقرة تزيد `search:clicks`، لا `listing:views` (صفحة الإعلان تعدّ الزيارة) |
| إشارة التفاعل تُصفَّر كل بضع دقائق (المفتاح القديم كانت تفرغه مزامنة المشاهدات) | عدّاد نقرات مستقل بمدة 30 يوماً |
| نتائج قديمة بعد بيع إعلان | الحالة مفهرسة وتُستبعد، وكاش البحث والإكمال التلقائي يُبطَل برفع رقم إصدار (O(1)) لا بـ `SCAN` على كل Redis |
| فهرس ناقص يحيّز المقارنة | `npm run search:reindex` في listings-service يعيد بناء الفهرس من Postgres على دفعات |
| إعلان «فائز» على ضجيج | لا حكم قبل 100 بحث لكل خوارزمية وفرق دالّ إحصائياً (اختبار z لنسبتين، ثقة 95%) |

## التشغيل

1. **بعد النشر:**
   ```
   docker compose exec listings-service node dist/scripts/reindex-search.js
   ```
   محلياً: `npm run search:reindex`.
2. **النتائج:** في `/admin/ranking`، تعرض عمليات البحث والنقرات ونسبة النقر لكل خوارزمية، والحكم الإحصائي، والإعلانات الأكثر نقراً، وعمليات البحث بلا نتائج.
3. **قبل الحسم:** اترك التجربة حتى تظهر عبارة «أفضل بفرق دالّ إحصائياً». عند إيقافها، يُثبَّت الترتيب الفائز في `RankingService.buildFunctionScore`.

## التحقق

- **اختبارات:**
  - search-service: الصفحات، واستبعاد المباع، وتجاهل الخوارزمية المفروضة، وعدّ الصفحة الأولى فقط، وعدم احتساب النقرة مشاهدة.
  - البوابة: `/search` خارج الكاش.
  - الويب: حفظ الترتيب، وإسقاط غير المنشور، والرجوع إلى قاعدة البيانات عند العطل فقط لا عند خطأ الطلب.
- **تشغيل فعلي عبر البوابة** على Postgres حقيقي:
  - Elasticsearch محاكى محلياً لتعذّر تنزيله في بيئة العمل؛ منطق الصلة وحده غير مختبَر هنا.
  - أُعيدت فهرسة 2,053 إعلاناً في 7.5 ثانية بلا فشل.
  - الخوارزمية ثابتة لكل زائر، والتوزيع عشوائي (24/16 على 40 زائراً).
  - الإعلان المباع لا يظهر، والصفحة الثانية لا تُعدّ.
  - في المتصفح: بحث «جوال» ثم نقرة على النتيجة الثانية سُجّلت بـ `position: 1` وخوارزميتها. ظهرت في `ab_test_results` وفي عدّاد النقرات، و`/admin/ranking` يعرض «لا يمكن الحكم بعد».
